# 要求仕様書: 概念と責務ごとのまとまりへの再構成

- 作成日: 2026-10-22
- 状態: 合意済み
- 関連: [計画](todo-refactoring.md)、ADR-0005（保存の形と遮断ルールのIDを固定する。計画のコミット7で書く）、[docs/decisions.md](../docs/decisions.md)のP5・P6（計画のコミット7で書く）

用語は[CONTEXT.md](../CONTEXT.md)に従う。この文書は「何を満たすか」だけを書き、「どう実現するか」は計画に書く。

## 1. 背景と問題

今のコードに、すぐ困る不具合はない。`src/core`は文の網羅率が100%で、いちばん大きいファイルでも175行である（2026-10-22に測定）。問題は、変更するときの読みにくさと、直し漏れの起きやすさにある。

- **一つの決定を、複数のモジュールで書いている。** 設定の項目の一覧を、7か所以上で書いている。`settings.ts`の型・既定値・`SETTING_NAMES`、`options.ts`の`SETTING_NAMES`と`readForm`、`content-script.ts`の全組み合わせとファイル名の数字の並び、`protection.ts`の`findNotices`である。`parseSettings`は、分割代入の順番が`SETTING_NAMES`の並びと一致することに頼っている。順番がずれても型エラーにならず、読み込んだ設定の値が入れ替わる。
- **技術の部品ごとに分けているので、一つの概念を読むのに複数のファイルを渡る。** ADR-0004（Service Workerが応答する遷移の遮断）は、5つのファイルに分かれている。`core/content-script.ts`の中身は、content scriptではなく、設定を渡すファイルの生成と登録である。
- **コードの名前が、用語集とそろっていない。** 警告ページは、コードで`blocked`、`warning page`、`blocked page`、`page blocked`の4通りに呼ばれている。e2eのテストは、遮断理由に`src`と違う値（`"idn" | "ip" | "userinfo"`）を使っている。
- **テスト用の警告ページのURLを、4か所で定義している。**
- **遮断ルールとURLでの判定の一致を確かめるテストが弱い。** 比べているのは「遮断するかどうか」だけで、試すURLは手で書いた一覧である。ルールのIDを変えても、このテストでは見つからない。

## 2. 目的

メンテナンスのしやすさと、人が読んだときの見通しを最優先にする。そのために、責務と概念ごとにコードをまとめる。直す場所を減らすことも目的に含むが、読みやすさを優先する。

## 3. 構造の要求

| ID   | 要求                                                                                                                                                                                                 |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SR-1 | 概念と責務ごとにフォルダを分ける。機能をつなぐまとめ役（`background.entry.ts`と`protection.ts`）は`src/`の直下に置き、概念はフォルダに置く                                                           |
| SR-2 | 遮断ルールとURLでの判定は、技術ごとの2つのモジュールのまま、`blocking/`に並べて置く。遮断理由ごとの表は作らない                                                                                      |
| SR-3 | 設定の項目は、手で書いた一つの表から、型・既定値・検証・全組み合わせ・設定を渡すファイルの名前・設定画面の読み書きを導く。項目の間の依存（プライベートIPアドレスの除外）と、通知の文言はコードに残す |
| SR-4 | 純粋なファイルと、ブラウザに触れるファイルを、ファイル名の末尾で見分ける。入口は`*.entry.ts`、ChromeのAPIを包むファイルは`*.chrome.ts`、DOMを扱うファイルは`*.dom.ts`とする                          |
| SR-5 | 次の境界の規則を、oxlintで守る                                                                                                                                                                       |
| SR-6 | コードの名前を、CONTEXT.mdの用語に合わせる。警告ページは`warning-page`とし、e2eの遮断理由の値を`src`にそろえる。`protection`は用語集に足さず、実装の名前として残す                                   |
| SR-7 | テスト用の警告ページのURLを、1か所（`test-support/warning-page.ts`）で定義する                                                                                                                       |
| SR-8 | 遮断ルールとURLでの判定の一致を、生成したURLの組み合わせと設定の8通りで確かめる。どのルールのIDで決まったかも確かめる。手で書いた一致のテストは、これに置き換える                                    |
| SR-9 | 今回の取り決めを文書に残す（7章）                                                                                                                                                                    |

SR-5の規則は次の3つである。

- R1: 純粋なファイル（SR-4の末尾を持たないファイル）は、実行時に`chrome`、`document`、`location`を使わない。型の位置で`chrome.*`を使うことは認める
- R2: フォルダは、共有のフォルダ（`blocking/`、`settings/`、`i18n/`）以外の兄弟のフォルダを読み込まない。`src/`の直下のまとめ役と、テストのファイル（`*.test.ts`）・`test-support/`は、この規則の対象外とする。テストの偽物は、テストする対象のフォルダを読み込む必要があり、本番のコードの境界とは関係しないため
- R3: 入口のファイル（`*.entry.ts`）は、どこからも読み込まない。`src/`の直下、テスト、`e2e/`、`scripts/`を含む、すべての`.ts`ファイルに適用する

`i18n/`は、警告ページと設定画面の両方が使うので、共有のフォルダに含める。

## 5. 制約

| ID  | 制約                                                                                                                                                                                         |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| C-1 | 利用者から見える振る舞い（画面の文言、警告ページのURL、権限）を変えない                                                                                                                      |
| C-2 | 保存の形（`chrome.storage.local`の`settings`のキーと項目名）と、遮断ルールのID（1〜9）を変えない（ADR-0005）                                                                                 |
| C-3 | ビルドが出力するファイルの名前（`blocked.html`・`blocked.js`・`blocked.css`、`background.js`、`content.js`、`options.html`・`options.js`・`options.css`、`content-settings/*.js`）を変えない |
| C-4 | 実行時の依存も、開発用の依存も足さない                                                                                                                                                       |
| C-5 | `settings-storage`と`localize`にユニットテストを足さない。網羅率の計測から外し、E2Eで確かめる今の方針を保つ                                                                                  |
| C-6 | E2Eはheadlessで流す。流す前に、ブラウザを起動する回数と、画面にウィンドウが出ないことを伝える                                                                                                |

## 6. 対象外

- 画面の文言・README・CONTEXT.mdの言葉をそろえること。「遮断」と「止める」、「遷移」と「移動」が混ざっている。将来の目標として、`docs/decisions.md`に記録する
- CONTEXT.mdの編集。「埋め込まれた文書」と「Service Workerが応答する遷移」を用語に足し、避けるべき語「拒否」（:44）を言い換え、全角と半角の間の空白をなくす。これは別のプルリクエストで行う
- 遮断理由ごとの表（SR-2）
- 保存の形の移行と、古い遮断ルールのIDを消す処理。C-2により要らない

## 7. 文書への反映

- ADR-0005: 保存の形と遮断ルールのIDは、利用者の環境に残るので、更新の前後で変えない。名前を変えて移行する案と比べて選んだ
- `docs/decisions.md`のP5: 概念と責務でフォルダを分け、まとめ役は`src/`の直下に置く
- `docs/decisions.md`のP6: ファイル名の末尾の付け方と、R1〜R3をoxlintで守る取り決め。R3はすべての`.ts`ファイルにかかる基底の規則として置く。同じファイルに二つの`overrides`が当たると、`no-restricted-imports`の設定は合わさらずに置き換わるので、R2の各規則にもR3を書き写すことと、R2の対象外（まとめ役、テスト、`test-support/`）と、R1はテストと`test-support/`にもかかることも書く
- `docs/decisions.md`の「将来の目標」: 画面の文言・README・CONTEXT.mdの言葉をそろえる

## 8. 根拠

- 遮断理由ごとの表の試作（2026-10-22、隔離したworktreeで実行）: 型チェックと334件のテストが通り、設定の8通りで遮断ルールが1バイトも違わなかった。ただ、表を束ねる側は`flatMap`と`filter`だけで、何も隠していなかった。優先度・パスワードを隠すルール・許可ルールの強さという遮断理由をまたぐ決定が3つのファイルに分かれ、一つの遮断理由のファイルだけで遮断の仕方が分かるのは、3つのうちIDNだけだった。浅い抽象と判定した（SR-2）
- 一致のテストの試作（2026-10-22、隔離したworktreeで実行）: 4,320通りのURLを設定の8通りで試す34,560件のテストが通り、テストの時間は約100ミリ秒増えた。本番のコードを一時的に壊して試すと、ルール8の番号の変更は新しいテストだけが見つけた。実装のブランチで同じ変更を試したときは、登録するIDの一覧を確かめている`protection.test.ts`も落ちた。プライベートの範囲を広げる変更は、二つの判定が同じパターンを使うので見つからず、範囲の端を確かめる今のテストが見つけた。URLの正規化はNodeの`new URL()`で行っており、Chromeと同じ結果かはブラウザで確かめていない
- oxlint 1.86（2026-10-22、試しのファイルで実行）: R1〜R3は`overrides`、`no-restricted-globals`、`no-restricted-imports`で書けた。型の位置の`chrome.*`は指摘されず、今の`src/core`への指摘は0件だった。dependency-cruiserはTypeScript 7に対応していない（Context7）
- 拡張機能の更新: 動的に追加した遮断ルールは更新後も残る（公式のドキュメント）。動的に登録したcontent scriptは更新で消える（ADR-0004、2026-10-20の測定。今回は測り直していない）
- 試作の差分は、`.claude/worktrees/agent-a91ed051770ec119d`（遮断理由ごとの表）と`.claude/worktrees/agent-a8b1fe88910eb31bc`（一致のテスト）に置いていた。どちらもコミットせず、PR #16のマージ後に消した。一致のテストは`src/blocking/block-rules-agreement.test.ts`として取り込んだ
