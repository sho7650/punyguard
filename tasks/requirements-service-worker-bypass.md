# 要求仕様書: Service Worker が応答する遷移の遮断

- 作成日: 2026-10-19
- 状態: 合意済み
- 関連: [計画](todo-service-worker-bypass.md)、[ADR-0004](../docs/adr/0004-content-script-blocks-service-worker-navigation.md)（実現方法）、[docs/decisions.md](../docs/decisions.md) の P3（現状の記録）

用語は [CONTEXT.md](../CONTEXT.md) に従う。この文書は「何を満たすか」だけを書き、「どう実現するか」は ADR-0004 と計画に書く。

## 1. 背景と問題

PunyGuard は、遮断理由（IDN ホスト・ユーザー情報付き URL・IP アドレスホスト）に当たる遷移を、ブラウザの遮断ルール（declarativeNetRequest）で警告ページに置き換えている。

しかし、そのサイトの Service Worker が応答する遷移には、遮断ルールが効かない。Service Worker はサイトのページが登録するもので、ページを閉じた後もブラウザに残り、以後の遷移に代わりに応答する。

1. 利用者が、攻撃者のサイト `evil.example` を一度でも普通に開く。サイトは、その時点で Service Worker を登録できる
2. 後日、利用者が `https://paypal.com@evil.example/` を開く
3. Service Worker がこの遷移に応答する。遮断ルールが効かないので、警告ページは出ず、攻撃者のページが表示され、そのスクリプトも動く

ユーザー情報付き URL では、遮断の対象は URL であってホストではない。そのため、ホスト自体のページは普通に開け、PunyGuard を入れた後でもこの手口が成り立つ。IDN ホストと IP アドレスホストでは、PunyGuard を入れる前（または、その遮断を無効にしていた間）に、そのホストを開いていた場合に限られる。

Service Worker は、遷移に応答する代わりに、別の URL へのリダイレクトを返すこともできる。リダイレクト先が遮断理由に当たらない URL であれば、最後に開いたページの URL だけを調べても遮断できない（2026-10-19 に測定。ユーザー情報付き URL は同じオリジン内へのリダイレクトでも、IDN ホストと IP アドレスホストは普通のホストへのリダイレクトで、すり抜けた）。

## 2. 目的

Service Worker が応答する遷移も、そうでない遷移と同じく遮断する。

## 3. 機能要求

| ID   | 要求                                                                                                                                                                                                                                                                                                         |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| FR-1 | Service Worker が応答する遷移のうち、遮断理由に当たるものを遮断する。対象は 3 つの遮断理由すべて（IDN ホスト・ユーザー情報付き URL・IP アドレスホスト）とする                                                                                                                                                |
| FR-2 | 遮断した遷移は、Service Worker が応答しない場合と同じ警告ページに置き換える                                                                                                                                                                                                                                  |
| FR-3 | ページ全体の遷移と、iframe の中の遷移の両方に適用する。iframe の中では、フレームの中身が警告ページになる。ただし、ユーザー情報付き URL の iframe は、Service Worker が応答する前にブラウザ自身が読み込みを拒否する。今の遮断と同じく警告ページにはならないが、読み込まれないことで遮断に含める（CONTEXT.md） |
| FR-8 | 警告ページへ移すとき、元の URL のパスワードは伏せる。今の遮断と同じく、警告ページのアドレスバーと履歴に平文のパスワードを残さない                                                                                                                                                                            |
| FR-4 | 利用者の設定に従う。ユーザー情報付き URL または IP アドレスホストの遮断を無効にしたら、その遮断理由だけに当たる遷移は、Service Worker が応答する場合も止めない。プライベート IP アドレスの除外も同じく効かせる                                                                                               |
| FR-5 | 設定の変更は、Service Worker が応答しない遷移と同じく、次の遷移から効かせる                                                                                                                                                                                                                                  |
| FR-6 | ブラウザの再起動後と、拡張機能の更新後も、FR-1〜FR-4、FR-8、FR-9 が効き続ける                                                                                                                                                                                                                                |
| FR-7 | 遮断の仕組みが働かない状態になったら（登録の失敗など）、今の遮断ルールの失敗と同じく、ツールバーの `!` バッジで知らせる                                                                                                                                                                                      |
| FR-9 | Service Worker がリダイレクトで応答した遷移も、元の遷移の URL が遮断理由に当たれば遮断し、警告ページに置き換える。ページ全体の遷移と iframe の中の遷移の両方に適用する。FR-4・FR-5・FR-8 もこの遷移に適用する                                                                                                |

## 4. 成功の基準

| ID   | 基準                                                                                                                                                                                                                                                                                       |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| AC-1 | 遮断理由に当たる、Service Worker が応答する遷移で、攻撃者のページを一瞬も描画させない                                                                                                                                                                                                      |
| AC-2 | 同じ遷移で、攻撃者のページのスクリプトを一切動かさない                                                                                                                                                                                                                                     |
| AC-3 | AC-1 と AC-2 を、1 回目の遷移から満たす。拡張機能の内部の状態（service worker が止まっているかなど）や、攻撃者の Service Worker の応答の仕方（ネットワークへの中継か、その場で作るか）によらず満たす。Service Worker がリダイレクトで応答した場合は、AC-1 と AC-2 の代わりに AC-4 を満たす |
| AC-4 | Service Worker がリダイレクトで応答した遷移は、1 回目から、拡張機能の service worker の状態によらず、最後に必ず警告ページに置き換わる                                                                                                                                                      |

## 5. 制約

| ID  | 制約                                                                                                              |
| --- | ----------------------------------------------------------------------------------------------------------------- |
| C-1 | インストール時と更新時の権限の警告文を増やさない                                                                  |
| C-2 | 外部と通信しない                                                                                                  |
| C-3 | ページの中身を読まない                                                                                            |
| C-4 | 「content script を置かない」という今の約束（README、ADR-0002）は変えてよい。変える場合は、README と ADR を改める |
| C-5 | 今の遮断（Service Worker が応答しない遷移、`<object>`・`<embed>` の中の文書を含む）の動作を変えない               |

## 6. 対象外（防げないと認める限界）

- Service Worker 自身のプログラムは、遷移に応答する時点で動きうる。これは README の既知の制限に書く
- 登録済みの Service Worker を削除することは行わない
- Service Worker がリダイレクトで応答した場合は、警告ページに置き換わる前に、リダイレクト先のページが表示され、そのスクリプトも動きうる。拡張機能の service worker が止まっていると起きる（測定では毎回起きた）。これは README の既知の制限に書く

## 7. 検証

| ID   | 検証方法                                                                                                                                                                                                                                                                                       |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| V-1  | E2E テストで、実際の手口どおりに確かめる。PunyGuard を入れる前にテスト用のサイトで Service Worker を登録し、その後で PunyGuard を入れて遷移させる                                                                                                                                              |
| V-2  | V-1 で、3 つの遮断理由それぞれについて、ページ全体の遷移と iframe の中の遷移で、警告ページになり、ページのスクリプトが動かないことを確かめる。ユーザー情報付き URL の iframe では、警告ページにならず、読み込まれず、スクリプトも動かないことを確かめる（FR-1〜FR-3、AC-1、AC-2）              |
| V-2a | V-1 で、ページ全体の遷移について、攻撃者の Service Worker の応答の仕方（中継型・自作型）と、拡張機能の service worker の状態（動作中・停止中）のすべての組み合わせを試す（AC-3）                                                                                                               |
| V-2b | パスワード付きの URL を Service Worker 経由で開いたとき、警告ページの URL のパスワードが伏せられていること、および履歴に平文のパスワードが残らないことを確かめる（FR-8）                                                                                                                       |
| V-2c | content script の登録が失敗したときに `!` バッジとツールチップで知らせることを、単体テストで確かめる（FR-7）                                                                                                                                                                                   |
| V-2d | V-1 で、リダイレクトで応答する Service Worker（同じオリジン内へ・普通のホストへ）を用意する。3 つの遮断理由、ページ全体と iframe、拡張機能の service worker の動作中と停止中のすべての組み合わせで、最後に警告ページになることを確かめる。パスワードを伏せることも確かめる（FR-9、AC-4、FR-8） |
| V-3  | 遮断を無効にした場合とプライベート IP アドレスを除外した場合に、Service Worker の応答が表示されることを確かめる（FR-4）。設定を切り替えた直後の遷移も確かめる（FR-5）                                                                                                                          |
| V-4  | ブラウザの再起動後と、拡張機能の再読み込み後にも効くことを確かめる（FR-6）                                                                                                                                                                                                                     |
| V-5  | 権限の警告文が増えないことを確かめる（C-1）                                                                                                                                                                                                                                                    |
| V-6  | 既存の単体テストと E2E テストがすべて通る（C-5）                                                                                                                                                                                                                                               |
