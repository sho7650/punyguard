# 要求仕様書: Service Workerが応答する遷移の遮断

- 作成日: 2026-10-19
- 状態: 合意済み
- 関連: [計画](todo-service-worker-bypass.md)、[ADR-0004](../docs/adr/0004-content-script-blocks-service-worker-navigation.md)（実現方法）、[docs/decisions.md](../docs/decisions.md)のP3（現状の記録）

用語は[CONTEXT.md](../CONTEXT.md)に従う。この文書は「何を満たすか」だけを書き、「どう実現するか」はADR-0004と計画に書く。

## 1. 背景と問題

PunyGuardは、遮断理由（IDNホスト・ユーザー情報付きURL・IPアドレスホスト）に当たる遷移を、ブラウザの遮断ルール（declarativeNetRequest）で警告ページに置き換えている。

しかし、そのサイトのService Workerが応答する遷移には、遮断ルールが効かない。Service Workerはサイトのページが登録するもので、ページを閉じた後もブラウザに残り、以後の遷移に代わりに応答する。

1. 利用者が、攻撃者のサイト`evil.example`を一度でも普通に開く。サイトは、その時点でService Workerを登録できる
2. 後日、利用者が`https://paypal.com@evil.example/`を開く
3. Service Workerがこの遷移に応答する。遮断ルールが効かないので、警告ページは出ず、攻撃者のページが表示され、そのスクリプトも動く

ユーザー情報付きURLでは、遮断の対象はURLであってホストではない。そのため、ホスト自体のページは普通に開け、PunyGuardを入れた後でもこの手口が成り立つ。IDNホストとIPアドレスホストでは、PunyGuardを入れる前（または、その遮断を無効にしていた間）に、そのホストを開いていた場合に限られる。

Service Workerは、遷移に応答する代わりに、別のURLへのリダイレクトを返すこともできる。リダイレクト先が遮断理由に当たらないURLであれば、最後に開いたページのURLだけを調べても遮断できない（2026-10-19に測定。ユーザー情報付きURLは同じオリジン内へのリダイレクトでも、IDNホストとIPアドレスホストは普通のホストへのリダイレクトで、すり抜けた）。

## 2. 目的

Service Workerが応答する遷移も、そうでない遷移と同じく遮断する。

## 3. 機能要求

| ID   | 要求                                                                                                                                                                                                                                                                                                  |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FR-1 | Service Workerが応答する遷移のうち、遮断理由に当たるものを遮断する。対象は3つの遮断理由すべて（IDNホスト・ユーザー情報付きURL・IPアドレスホスト）とする                                                                                                                                               |
| FR-2 | 遮断した遷移は、Service Workerが応答しない場合と同じ警告ページに置き換える。ただし、ユーザー情報付きURLへの遷移に、Service Workerがネットワークへの中継で応答した場合は、ブラウザ自身が遷移を失敗させ、エラーページになる。警告ページにはならないが、攻撃者のページは読み込まれないので、遮断に含める |
| FR-3 | ページ全体の遷移と、iframeの中の遷移の両方に適用する。iframeの中では、フレームの中身が警告ページになる。ただし、ユーザー情報付きURLのiframeは、Service Workerが応答する前にブラウザ自身が読み込みを拒否する。今の遮断と同じく警告ページにはならないが、読み込まれないことで遮断に含める（CONTEXT.md） |
| FR-8 | 警告ページへ移すとき、元のURLのパスワードは伏せる。今の遮断と同じく、警告ページのアドレスバーと履歴に平文のパスワードを残さない                                                                                                                                                                       |
| FR-4 | 利用者の設定に従う。ユーザー情報付きURLまたはIPアドレスホストの遮断を無効にしたら、その遮断理由だけに当たる遷移は、Service Workerが応答する場合も止めない。プライベートIPアドレスの除外も同じく効かせる                                                                                               |
| FR-5 | 設定の変更は、Service Workerが応答しない遷移と同じく、次の遷移から効かせる                                                                                                                                                                                                                            |
| FR-6 | ブラウザの再起動後と、拡張機能の更新後も、FR-1〜FR-4、FR-8、FR-9が効き続ける                                                                                                                                                                                                                          |
| FR-7 | 遮断の仕組みが働かない状態になったら（登録の失敗など）、今の遮断ルールの失敗と同じく、ツールバーの`!`バッジで知らせる                                                                                                                                                                                 |
| FR-9 | Service Workerがリダイレクトで応答した遷移も、元の遷移のURLが遮断理由に当たれば遮断し、警告ページに置き換える。ページ全体の遷移とiframeの中の遷移の両方に適用する。FR-4・FR-5・FR-8もこの遷移に適用する                                                                                               |

## 4. 成功の基準

| ID   | 基準                                                                                                                                                                                                                                                                          |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AC-1 | 遮断理由に当たる、Service Workerが応答する遷移で、攻撃者のページを一瞬も描画させない                                                                                                                                                                                          |
| AC-2 | 同じ遷移で、攻撃者のページのスクリプトを一切動かさない                                                                                                                                                                                                                        |
| AC-3 | AC-1とAC-2を、1回目の遷移から満たす。拡張機能の内部の状態（service workerが止まっているかなど）や、攻撃者のService Workerの応答の仕方（ネットワークへの中継か、その場で作るか）によらず満たす。Service Workerがリダイレクトで応答した場合は、AC-1とAC-2の代わりにAC-4を満たす |
| AC-4 | Service Workerがリダイレクトで応答した遷移は、1回目から、拡張機能のservice workerの状態によらず、最後に必ず警告ページに置き換わる                                                                                                                                             |

## 5. 制約

| ID  | 制約                                                                                                          |
| --- | ------------------------------------------------------------------------------------------------------------- |
| C-1 | インストール時と更新時の権限の警告文を増やさない                                                              |
| C-2 | 外部と通信しない                                                                                              |
| C-3 | ページの中身を読まない                                                                                        |
| C-4 | 「content scriptを置かない」という今の約束（README、ADR-0002）は変えてよい。変える場合は、READMEとADRを改める |
| C-5 | 今の遮断（Service Workerが応答しない遷移、`<object>`・`<embed>`の中の文書を含む）の動作を変えない             |

## 6. 対象外（防げないと認める限界）

- Service Worker自身のプログラムは、遷移に応答する時点で動きうる。これはREADMEの既知の制限に書く
- 登録済みのService Workerを削除することは行わない
- Service Workerがリダイレクトで応答した場合は、警告ページに置き換わる前に、リダイレクト先のページが表示され、そのスクリプトも動きうる。拡張機能のservice workerが止まっていると起きる（測定では毎回起きた）。これはREADMEの既知の制限に書く
- ユーザー情報付きURLへの遷移をService Workerが中継した場合（FR-2のただし書き）、タブの履歴（「戻る」）とエラーページのアドレスバーに、平文のパスワード付きのURLが残る。ブラウザ自身の動作で、PunyGuardの有無によらない。拡張機能はエラーページに手を出せず、`tabs.update`で警告ページへ移しても、元の項目は「戻る」に残った（2026-10-20、10回中10回）。ブラウザの履歴（`chrome.history`）には残らない。これはREADMEの既知の制限に書く
- 拡張機能の更新（開発中の再読み込みを含む）の直後、content scriptを登録し直すまでのごく短い間（測定では70〜83ミリ秒）は、Service Workerが応答する遷移を遮断できない。更新でcontent scriptの登録が消えるため（2026-10-20、5回中5回）。遮断ルールは更新後も残るので、Service Workerが応答しない遷移には影響しない。ブラウザの再起動では登録が残り、最初の遷移から効く（10回中10回）。これはREADMEの既知の制限に書く

## 7. 検証

| ID   | 検証方法                                                                                                                                                                                                                                                                                 |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| V-1  | E2Eテストで、実際の手口どおりに確かめる。PunyGuardを入れる前にテスト用のサイトでService Workerを登録し、その後でPunyGuardを入れて遷移させる                                                                                                                                              |
| V-2  | V-1で、3つの遮断理由それぞれについて、ページ全体の遷移とiframeの中の遷移で、警告ページになり、ページのスクリプトが動かないことを確かめる。ユーザー情報付きURLのiframeでは、警告ページにならず、読み込まれず、スクリプトも動かないことを確かめる（FR-1〜FR-3、AC-1、AC-2）                |
| V-2a | V-1で、ページ全体の遷移について、攻撃者のService Workerの応答の仕方（中継型・自作型）と、拡張機能のservice workerの状態（動作中・停止中）のすべての組み合わせを試す（AC-3）                                                                                                              |
| V-2b | パスワード付きのURLをService Worker経由で開いたとき、警告ページのURLのパスワードが伏せられていること、および履歴に平文のパスワードが残らないことを確かめる（FR-8）                                                                                                                       |
| V-2c | content scriptの登録が失敗したときに`!`バッジとツールチップで知らせることを、単体テストで確かめる（FR-7）                                                                                                                                                                                |
| V-2d | V-1で、リダイレクトで応答するService Worker（同じオリジン内へ・普通のホストへ）を用意する。3つの遮断理由、ページ全体とiframe、拡張機能のservice workerの動作中と停止中のすべての組み合わせで、最後に警告ページになることを確かめる。パスワードを伏せることも確かめる（FR-9、AC-4、FR-8） |
| V-3  | 遮断を無効にした場合とプライベートIPアドレスを除外した場合に、Service Workerの応答が表示されることを確かめる（FR-4）。設定を切り替えた直後の遷移も確かめる（FR-5）                                                                                                                       |
| V-4  | ブラウザの再起動後と、拡張機能の再読み込み後にも効くことを確かめる（FR-6）                                                                                                                                                                                                               |
| V-5  | 権限の警告文が増えないことを確かめる（C-1）                                                                                                                                                                                                                                              |
| V-6  | 既存の単体テストとE2Eテストがすべて通る（C-5）                                                                                                                                                                                                                                           |
